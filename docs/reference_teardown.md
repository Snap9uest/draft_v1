## 1. 한 줄 요약

**Jam Social에서는 "판정을 없애는 법"이 아니라 "판정이 실패해도 파티가 안 멈추는 폴백 사다리"를 훔치고, Picapica에서는 "네컷다움을 만드는 여백 비율 5개와 iOS 저장 경로"를 훔친다. 둘 다 우리보다 야심이 작아서 실패한 지점(Jam의 죽은 TV 화면, Picapica의 2등 시민 업로드 모드)이 정확히 우리 F4·F7의 차별점이다.**

다섯 줄 버전:

1. Jam은 사진을 버리고 QR 근접성으로 인증을 치환했다 — 우리는 AI 비전을 쓰지만, 그들의 **실패 폴백 10종**은 통째로 가져온다.
2. Jam의 TV 화면은 게임 내내 정적인 조인 QR 게시판이다. **우리 F4가 이길 수 있는 유일하고 가장 값싼 지점.**
3. Jam의 "프롬프트 수 = 시간 = 가격" 단일 축과 **프롬프트 풀 / 1인 배정량 분리**는 F2·F9에 그대로 이식된다.
4. Picapica의 네컷다움은 폰트가 아니라 **하단 비대칭 여백(위의 2.25배) + 캡션 각인 한 줄**에서 나온다. 상수 5개가 전부다.
5. Picapica는 `toDataURL`로 맞고 `toBlob`으로 고쳤고, 소스맵에 그 주석을 남겼다 — **iOS Safari 저장 경로는 첫날부터 blob.**

## 2. The Jam Social에서 가져올 것

### 2-A. F2 (AI 개인화 빙고판)에 매핑

#### ① 격자는 정체성으로 두되, 플레이는 "프롬프트 큐"로

**[무엇을]** Jam에는 격자가 아예 없다. 화면에 현재 미션 **딱 1개**를 대형 볼드로 띄우고, 진행은 프롬프트 개수만큼 균등 분할된 세그먼트 바(현재 칸만 pulse)로 표현한다. 전체 목록은 별도 모달로 열리고 `Done` / `In Progress` / `Still to Go` 3섹션 아코디언 + 각 섹션에 개수 배지 `(N)`. 기본 접힘 상태가 섹션별로 다르다(`Done` 접힘, `Still to Go` 펼침).

**[왜]** 모바일 세로 화면에서 3×3 격자를 탭 타깃으로 쓰면 칸 하나가 100px 남짓이라 미션 문구가 2~3글자밖에 안 들어간다. Jam은 그 씨름을 통째로 회피했다. 우리 미션은 "○○님과 케미샷" 같은 고유명사 포함 문장이라 **격자 칸 안에서 절대 읽히지 않는다.**

**[우리 어디에]** F2 폰 화면을 2층으로:
- **상단 = 3×3 미니맵** (칸당 40~48px, 상태색만 — 미완료/판정중/완료). 우리 정체성이자 "빙고"의 시각적 증거. 탭하면 해당 칸으로 점프.
- **하단 = 현재 미션 카드 1장** (대형 볼드 + 촬영 버튼). 실제 플레이는 여기서만 일어난다.
- 전체 목록은 미니맵 탭 → 3섹션 아코디언 모달. `완료(N)` / `진행 중(1)` / `남은 미션(N)`.

명세의 "3×3 판(칸 상태: 미완료/판정 중/완료)"은 미니맵이 충족한다. 격자를 포기하는 게 아니라 **격자의 역할을 조작 UI에서 진행 지표로 강등**하는 것.

#### ② 미션 문구 2단 구조 — `[시각적으로 즉시 판별 가능한 타깃] + [구체적 행동/질문]`

**[무엇을]** Jam의 프롬프트 수백 개가 예외 없이 이 구조다. `Find someone who…` / `Ask someone…` / `Challenge someone to…` 세 동사가 전체의 95% 이상. 그리고 **"찾기"에서 절대 끝내지 않는다** — 반드시 질문이나 행동이 붙어 최소 1턴의 대화를 강제한다. 거절 비용이 0에 가깝다(신체 접촉·노출·창피 유발 없음, 최악의 경우 "아니요" 한마디).

**[왜]** 우리 F2의 수용 기준 2번("전부 동의 기반 '함께 찍기'이며 도촬류 0건")은 *금지* 조건만 걸어놓았다. 금지만으로는 LLM이 "즐거운 순간을 담아보세요" 같은 무해하지만 실행 불가능한 문구를 뱉는다. **실행 가능성을 강제하는 양성 조건**이 필요하다.

**[우리 어디에]** `src/lib/ai/prompts.ts`의 빙고판 생성 프롬프트에 출력 스키마로 못 박는다:

```
미션 = [상대 지정] + [함께 하는 구체 행동] + [사진으로 확인 가능한 증거]
  상대 지정: 참가자 닉네임 직접 지정 or 시각적 조건("아직 인사 안 한 사람")
  행동:     동사 3종으로만 시작 — "…와 함께 찍기" / "…에게 부탁해서 찍기" / "…와 도전해서 찍기"
  증거:     AI 비전이 판정할 수 있어야 함 (2인 이상 프레임 / 특정 사물 / 특정 포즈)
```

세 번째 조건이 결정적이다 — **AI 비전 판정기가 판정할 수 없는 미션은 애초에 생성되면 안 된다.** "○○님과 진심 어린 대화 나누기"는 판정 불가라서 곧바로 셀프체크 폴백으로 새고, 그러면 F3의 자동 인증이라는 차별점이 무너진다. 미션 생성 시점에 판정 가능성을 강제하는 게 F3을 살린다.

#### ③ `[대괄호]` 경량 마크업 — 본 미션 + 부가 코칭 한 줄

**[무엇을]** Jam은 프롬프트 문자열 안에서 `[대괄호]`로 감싼 부분을 줄바꿈 + 작고 얇은 글씨로 렌더한다(중첩도 depth 카운터로 처리).

**[왜]** 미션 텍스트 하나로 "무엇을" + "어떻게 하면 쉬운지"를 같이 저작할 수 있다. LLM이 한 필드에 두 층을 담게 되고, 스키마를 늘릴 필요가 없다.

**[우리 어디에]** F2 미션 생성 스키마에 필드를 추가하지 말고 대괄호 문법 하나로 처리. `src/lib/db/types.ts`의 `BoardCell.mission`은 그대로 `string`. 렌더 시 `mission.split(/\[|\]/)` 수준의 5줄짜리 파서로 충분. — **스키마 추가 대비 확실히 더 게으른 선택.**

예: `민준님과 하이파이브 순간 포착 [둘 다 프레임에 들어오게, 셀카봉 없으면 지나가는 사람한테 부탁!]`

#### ④ 60초 지연 Skip — 지연 + 랜덤 점프 + 쿨다운 3중 조합

**[무엇을]** Skip 버튼이 처음부터 없다. `setTimeout(…, 60000)` 후에만 나타나고, 누르면 **다음 것이 아니라 남은 미션 중 랜덤한 뒤쪽 인덱스로 점프**하고, 누른 직후 다시 숨겨져 60초 후 재등장한다.

**[왜]** 스킵을 아예 막으면 막힌 사람이 이탈하고, 항상 열어두면 연타로 게임을 통과해버린다. 셋 다 필요한 이유가 각각 있다: 지연 = 연타 방지, 랜덤 뒤쪽 = 순차 스킵으로 판을 비우는 것 방지, 쿨다운 = 스킵 후 재스킵 방지.

**[우리 어디에]** F2 미션 카드에 "다른 미션 보기". 우리 3×3에서는 랜덤 점프 대신 **미완료 칸 중 랜덤 1칸으로 커서 이동**. 로컬 상태만 쓰므로 DB 변경 0.

#### ⑤ 미션 풀 / 1인 배정량 분리

**[무엇을]** Jam은 호스트가 프롬프트를 무제한 넣을 수 있고, 참가자마다 그 풀에서 **다른 랜덤 서브셋 N개**를 받는다. 순서도 참가자마다 셔플.

**[왜]** 호스트가 "미션을 더 넣으면 게임이 길어진다"는 걱정 없이 마음껏 쓴다. 그리고 옆 사람과 미션이 겹치지 않는다.

**[우리 어디에]** 우리는 LLM이 인당 9개를 개별 생성하므로 이미 겹치지 않는다 — 이 축은 **폴백 경로에만** 적용한다. F2 예외 슬롯의 "프리셋 미션 풀에서 자동 구성 폴백"이 정확히 여기다. 프리셋 풀을 톤 프리셋별 30~40개로 잡고, 폴백 시 **참가자 id를 seed로 한 결정적 셔플**로 9개를 뽑으면 LLM이 죽어도 각자 다른 판이 나온다. F2 수용 기준 1번("전원 동일 판 없음")이 **폴백 경로에서도 지켜진다** — 지금 명세대로 프리셋 풀에서 그냥 뽑으면 폴백 시 전원 같은 판이 될 위험이 있다. 이건 명세의 구멍이다.

### 2-B. F3 (사진 인증)에 매핑

#### ⑥ 폴백 사다리 — Jam이 코드로 갖춘 10종 전부

**[무엇을]** 아래가 Jam 번들에서 실제 확인된 실패 경로별 폴백 전부다.

| Jam의 실패 | Jam의 폴백 | SnapQuest 대응 |
|---|---|---|
| 카메라 권한 거부 | 4자리 코드 수동 입력 (`Trouble Scanning?`) | **앨범 업로드 경로** (F3 예외에 이미 있음) |
| 서버 429 폭주 | "인기라서 그렇다"로 리프레이밍 + 재시도 유도 | **AI API rate limit 시 동일 리프레이밍** (신규) |
| 미션이 막힘 | 60초 후 Skip 등장, 랜덤 점프, 쿨다운 | ④ 위 |
| 자기 QR 스캔 | 농담 문구 후 내 프로필로 | (해당 없음) |
| 데스크톱 조인 시도 | 대형 화면 페이지로 리다이렉트 | **`?role=tv`로 안내** (F9와 정합) |
| 이벤트 전날 접속 | Test Mode 자동 ON, 당일 자동 OFF | ⑫ 아래 |
| 브랜드 색이 밝아 QR 대비 부족 | 상대휘도 계산 후 자동 어둡게 | ⑬ 아래 |
| 뒤로가기·새로고침 | `?fromSpreadList=true` 쿼리 플래그로 중복 카운트 차단 | ⑦ 아래 |
| 네트워크 실패 | **에러 안 띄우고 로컬 인덱스만 증가시켜 진행** | ⑧ 아래 |
| 계정 소실 위험 | 로그아웃 버튼 옆 이메일 등록 경고 | ⑨ 아래 (단, 타이밍은 다르게) |

**[왜]** 이건 아이디어가 아니라 **규모 있는 오프라인 이벤트를 실제로 겪어본 팀의 흔적**이다. 하나씩 발명하는 것보다 목록째 훔치는 게 압도적으로 싸다.

#### ⑦ URL 쿼리 플래그로 멱등성 — 서버 dedupe 테이블 없이

**[무엇을]** Jam은 연결 처리 후 `router.push(pathname + "?fromSpreadList=true")`. 이 쿼리가 붙어 있으면 다시 카운트하지 않는다. **URL을 멱등성 토큰으로 쓴다.**

**[왜]** 뒤로가기·새로고침·React 재렌더로 인한 이중 집계를 서버 테이블 없이 막는다. 우리는 `photos` 테이블에 dedupe 인덱스를 추가하지 않아도 된다.

**[우리 어디에]** F3의 업로드 완료 → 칸 완료 처리 경로. 업로드 성공 후 `router.replace(?verified=<photo_id>)`. 마운트 시 이 값이 현재 칸의 `photoId`와 같으면 **재판정 API를 호출하지 않는다.** 판정 API가 한 장당 1회라는 F3 비즈니스 규칙(원가 통제)이 새로고침으로 깨지는 걸 막는 가장 게으른 방법.

#### ⑧ 네트워크 실패 시 낙관적 진행 — 데이터 정합성보다 현장 흐름

**[무엇을]** Jam은 상대 코드 조회가 fetch 레벨에서 실패하면 **에러를 띄우는 대신 로컬 인덱스를 그냥 증가시키고 화면을 갱신한다.** 행사장 와이파이가 죽어도 게임이 멈추지 않는다.

**[왜]** 파티장 와이파이는 반드시 죽는다. 200명이 동시에 5G/와이파이를 물면 업로드가 30초씩 걸린다. 그 순간 "업로드 실패" 모달이 뜨면 그 사람의 게임은 끝난다.

**[우리 어디에]** F3에서 **로컬 미리보기 즉시 반영 + 백그라운드 업로드 큐**. 명세의 "업로드 실패 → 재시도 버튼 + 로컬 미리보기 유지"를 한 단계 더 밀어서, 칸 상태를 낙관적으로 `judging`으로 전환하고 미리보기를 칸에 박아둔다. 업로드가 끝나면 조용히 실제 URL로 교체. F1의 캐릭터 생성이 이미 비차단인 것과 같은 원리 — **우리 명세는 캐릭터 생성만 비차단이고 사진 업로드는 차단**인데, 그게 더 자주 발생하는 마찰이다.

#### ⑨ 세션 토큰 소실 경고를 "가치가 생긴 직후"에 — Jam의 실수를 뒤집어서

**[무엇을 / 왜]** Jam은 이름 한 칸으로 계정을 만들고, 그 계정이 **디바이스에만 존재**한다는 사실을 게임이 끝난 뒤 설정 화면 경고문으로 알린다. 브라우저 데이터가 지워지면 그날의 연결 기록이 통째로 사라진다. **핵심 가치(만난 사람 목록)가 가장 휘발성 높은 저장소에 있다.**

우리도 정확히 같은 구조다 — `participants.session_token`이 localStorage에만 있고, 티켓·칭호·내 갤러리 전부가 그 토큰에 매달려 있다. F8 예외에 "세션 토큰 유실 → 닉네임 재확인으로 복원"이 있지만, 같은 방에 동명이인이 있으면 무너진다.

**[우리 어디에]** 이메일을 받자는 게 아니다(로그인 없음이 우리 정체성). **가치가 생긴 직후**에 방 링크 저장을 유도한다:
- **첫 미션 인증 성공 직후** — "이 링크 저장해두세요. 내 사진·티켓이 여기 있어요" + 복사 버튼 (링크에 `?s=<session_token>` 포함).
- F8 아카이브 복원의 1차 수단을 "닉네임 재확인"이 아니라 **토큰 포함 링크**로 바꾼다. 닉네임 재확인은 2차 폴백.
- 완주 후는 이미 늦다 — 그때 사람들은 폰을 주머니에 넣는다.

#### ⑩ 429를 1급 시민으로 — 실패를 사회적 증거로 리프레이밍

**[무엇을]** Jam은 `TOO_MANY_REQUESTS = 429`를 별도 모듈로 두고, join / 연결 / 계정생성 **각 경로에 전용 사과 문구**를 갖고 있다. 취지는 "동시에 너무 많이 몰렸다" — 실패가 아니라 인기의 증거로 프레이밍한다.

**[왜]** 우리 리스크 표에 이미 "LLM rate limit·비용 폭주"가 있다. Gemini API는 무료/저티어에서 분당 요청 제한이 실재하고, **파티 시작 5분간 15명이 동시에 입장하면 캐릭터 + 빙고판 = 30콜이 한꺼번에 간다.** 이게 우리의 부하 피크다.

**[우리 어디에]** `src/lib/ai/gemini.ts`에 429 분기. 세 경로에 각각 문구:
- F1 캐릭터: 조용히 프리셋 아바타 (사용자에게 알리지 않음 — 이미 비차단)
- F2 빙고판: 프리셋 풀 폴백 (조용히)
- F3 판정: **"지금 다들 사진 올리는 중! 잠깐 셀프 체크로 넘어갈게요"** → 셀프체크 버튼 즉시 노출. 유일하게 사용자에게 보이는 경로이므로 여기만 문구를 쓴다.

### 2-C. F9 (호스트 도구) + F4 (TV)에 매핑

#### ⑪ 멀티라인 붙여넣기 → 줄 단위 파싱 (미션 편집)

**[무엇을]** Jam의 미션 편집은 폼 반복이 아니라 **큰 textarea에 통째로 붙여넣고 `Add` 한 방** → 줄 단위로 파싱되어 번호 목록이 된다. 각 항목에 `remove` 링크만. 성공 토스트.

**[왜]** F2 수용 기준 3번("호스트가 개별 미션을 수정할 수 있다")을 만족시키는 가장 게으른 UI다. 인라인 편집 폼 9개를 만들 필요가 없다. `textarea.value.split("\n").filter(Boolean)` 한 줄.

**[우리 어디에]** F9 호스트 폰 컨트롤 뷰의 미션 수정. 우리는 인당 9칸이 다 다르므로 **톤 프리셋의 시드 미션 풀 편집**에 쓴다. 개별 참가자 판 수정은 넣지 않는다 — YAGNI, 호스트가 15명 판을 하나씩 고칠 리 없다.

#### ⑫ Quick Setup 템플릿 — 빈 화면을 절대 보여주지 않는다

**[무엇을]** Jam의 방 생성 첫 화면은 템플릿 그리드(Work Event 💼 / Networking 🕸️ / Dating Mixer 💌 / Social Mixer 💬 / 대학 동아리 / …). **클릭하면 예시 프롬프트 3개가 즉시 채워진다.** 이벤트명에도 예시 문구가 프리필. FAQ 기준 셋업 2분.

**[왜]** 우리 F9 수용 기준 1번이 "방 생성부터 QR 표시까지 클릭 3회 이내". 톤 프리셋을 **템플릿 카드 그리드로 만들면 클릭 1회에 톤 + 시드 미션 + 방 이름이 전부 정해진다.** 지금 명세는 "톤 프리셋 선택(기본값 제공)"이라 드롭다운을 상상하기 쉬운데, 카드 그리드가 훨씬 빠르고 빈 화면이 없다.

**[우리 어디에]** F9 방 생성 화면 = 톤 프리셋 카드 3~4장(친목 / 동아리 OT / 워크샵 / 브랜드 행사) + "방 만들기" 버튼. 카드 클릭 = 톤 + 프리셋 미션 풀 + 방 이름 프리필 동시 확정.

#### ⑬ Test Mode 자동 해제 — 호스트가 당일에 아무것도 안 눌러도 되게

**[무엇을]** Jam은 시작/정지 버튼이 없다. `start_datetime` 기준으로 이벤트 전날까지 Test Mode가 자동 ON, 당일 자동 OFF. 배너 문구가 명시적으로 "당신은 아무것도 안 해도 됩니다"라고 말한다.

**[왜]** 호스트가 "테스트 모드 끄기"를 잊어서 행사가 망하는 시나리오를 날짜로 없앤 것. 우리 F9 예외에 "종료 미처리로 방치 → 보관 만료 시점에 자동 종료 처리 폴백"이 이미 같은 사고를 하고 있다.

**[우리 어디에]** 우리는 즉석 방 생성이라 `start_datetime`이 없다. 대신 같은 정신을 **데모 방 자동 리셋**에 쓴다 — 심사관이 데모 방을 어지럽혀도 N분 후 시드 상태로 자동 복귀. F8 수용 기준 3번의 "보관 시계를 분 단위로 단축한 데모 방"과 같은 축이므로 시계 압축 유틸 하나를 공유한다.

#### ⑭ QR 대비 안전장치 — 커스텀 색이 스캔 실패를 유발하지 않게

**[무엇을]** Jam은 브랜드 primary_color의 **상대휘도를 계산해 150 초과면 200만큼 어둡게 낮춰서** QR 전경색으로 쓴다.

**[왜]** 빔프로젝터는 대비가 모니터보다 훨씬 나쁘다. 우리 TV 뷰가 브랜드 색을 쓰거나 어두운 파티 조명 아래 흰 배경에 밝은 QR을 그리면 스캔이 실패하고, **F1의 입장 경로 자체가 죽는다.**

**[우리 어디에]** F9의 TV QR 렌더. 색을 커스터마이즈 안 할 거면 **QR은 무조건 순검정 on 순백**으로 고정하고 끝낸다 — 계산 코드조차 필요 없다. 커스텀 프레임(§4 유료)이 들어오는 시점에만 휘도 계산을 붙인다.

#### ⑮ 호스트 셀프 온보딩 — 호스트가 자기 폰으로 게스트 경험을 완주

**[무엇을]** Jam의 `/dashboard/get-started`는 체크리스트 위저드다. QR 스캔 → 이름 입력 → 튜토리얼 → **더미 플레이어("Tracy", "Paul")의 QR이 화면에 실제로 렌더되어 그걸 스캔** → 프롬프트 수정 → CTA. 각 단계에 "이 단계 했음 →" 버튼.

**[왜]** 우리 §5 데모 시나리오가 이미 이 구조다(탭 3개 + 봇 참가자). **Jam은 이걸 호스트 온보딩에 썼고 우리는 심사관 데모에 쓴다 — 같은 자산이다.** 랜딩의 tv/host/player 링크 3개 = Jam의 위저드 단계. 봇 참가자 = Tracy/Paul.

**[우리 어디에]** 추가 구현 없음. **§5 데모 시나리오를 그대로 정식 호스트 온보딩으로 재사용한다**는 확인. 랜딩 3링크에 "① 먼저 TV를 띄우세요 ② 폰으로 입장해보세요 ③ 호스트 조작을 해보세요" 순번 라벨만 붙이면 위저드가 된다.

#### ⑯ TV 화면을 상태 전이시킨다 — Jam이 실패한 지점 = 우리 F4의 차별점

**[무엇을 / 왜]** Jam의 현장 스크린(`/bingo/<slug>`)은 게임 내내 **정적**이다. 조인 QR + 코드 + 앱 스크린샷 2장 + 유튜브 영상. 30분이 지나도 화면이 똑같다. 방 안에서 벌어지는 일(몇 명이 조인했는지, 연결이 몇 개 생겼는지, 누가 앞서는지)은 **호스트 대시보드에만 있고 방에는 없다.** 그리고 실시간 인프라가 0이라(WebSocket·SSE·폴링 전부 0건) 구조적으로 그럴 수밖에 없다.

**큰 화면은 오프라인 이벤트에서 가장 값싼 참여 엔진**이고, Jam은 그걸 통째로 놀리고 있다. 이게 우리에게 열려 있는 가장 큰 틈이다.

**[우리 어디에]** F4/F9의 TV 뷰를 방 status에 따라 4단계로 명시적으로 전이시킨다. `rooms.status`가 이미 `lobby / live / award / ended` 4상태로 존재하므로 **스키마 변경 0, 라우팅 분기 하나**로 끝난다:

| status | TV 화면 |
|---|---|
| `lobby` | QR **대형** 중앙 + 캐릭터 그리드 채워지는 중 + 사회자 소개 멘트 |
| `live` | QR **축소해 구석**으로 + 포토월 그리드(신규 강조) + 참가자 수·인증 수 카운터 + 사회자 리액션 배너 |
| `award` | 칭호 발표 연출 + 베스트샷 후보 + 실시간 득표 |
| `ended` | 단체 프레임 1장 + 리더보드 + 앨범 QR |

명세 F4 표시 슬롯에 "로비→포토월→시상→엔딩 연출"이 이미 있으므로 **새 기능이 아니라 우선순위 확인**이다. 늦게 온 사람이 "지금 뭐가 진행 중인지" 알 수 있어야 하고, 카운터가 올라가는 걸 다 같이 보는 순간이 집단 모멘텀을 만든다.

**Realtime 구독 대상은 TV 1대뿐.** 플레이어는 구독하지 않는다 — 200명 구독이 아니라 1명 구독. Supabase Realtime 동시 연결 한도를 지키는 유일한 설계다. (Jam의 429 문구가 정확히 이 경합의 증상이었다.)

## 3. Picapica에서 가져올 것 — F7 (엔딩 네컷 티켓)

### 3-A. "네컷다움"의 정확한 수치

Picapica의 합성 상수는 딱 5개다(단위 px, 캔버스 폭 480 기준):

```
셀 크기        가로형 400×300  |  세로형 300×400
borderSize     40   (사방 여백)
photoSpacing   15   (컷 사이 간격)
textHeight     50   (하단 캡션 전용 추가 높이)
캡션 1행       20px
각인 2행       12px, 알파 0.5
```

여기서 나오는 **비율 3개가 네컷다움의 전부**다:

| 비율 | 값 | 의미 |
|---|---|---|
| **하단 여백 / 상단 여백** | `(40+50)/40 = 2.25` | 아래쪽 "턱(ledge)". 캡션 자리이자 **"인화된 물건"으로 보이게 하는 핵심.** 사방 균등이면 그냥 콜라주가 된다 |
| **외곽 여백 / 컷 간격** | `40/15 = 2.7` | 사진들이 서로 붙어 한 덩어리로 묶이고, 그 덩어리가 프레임 안에 떠 있는 형태 |
| **컷 폭 / 캔버스 폭** | `400/480 = 83%` (세로형 79%) | 좌우 여백은 폭의 8~10%뿐 |

**각인(engraving) 2행 구조:**
- 1행: `브랜드 + 날짜 + 시각`을 **한 줄에 붙여서**, 가운데 정렬, y = `높이 - 40`. 글자 크기 = 캔버스 폭의 **4.2%**
- 2행: 저작권 미세각인, 알파 0.5, y = `높이 - 20`, 우측. 글자 크기 = 폭의 **2.5%**. 읽히기보다 "질감"으로 존재

**"이 순간을 기록했다"는 감각은 전부 이 캡션 한 줄에서 나온다. 날짜/시각이 없으면 그냥 사진 콜라주다.** [원 조사자 판단이지만 동의]

### 3-B. SnapQuest 티켓 규격 — 위 비율을 1080×1920에 이식

**중요한 계산 결과 하나:** Picapica의 세로 4컷 스트립(Layout E)은 비율 **1:4.67**이다. 폭 1080이면 높이 5040 → **인스타 스토리(1080×1920)에 절대 안 들어간다.** 명세가 "인스타 스토리 규격"을 요구하므로 **4컷 세로 스트립은 구조적으로 불가능하고, 2×2 그리드가 유일한 답이다.** 이건 디자인 취향이 아니라 산술이다.

캔버스 폭 `W = 1080` 기준, Picapica 비율을 그대로 적용한 상수:

```
BORDER   = 0.083 · W  →  90    (40/480)
SPACING  = 0.031 · W  →  34    (15/480)
LEDGE    = 0.104 · W  → 112    (50/480, 하단에만 BORDER에 추가)
CAPTION  = 0.042 · W  →  45px  (각인 1행)
MICRO    = 0.025 · W  →  27px  (각인 2행, 알파 0.5)
```

**절대 픽셀 상수를 코드에 쓰지 말고 전부 `W` 비율로 계산할 것.** Picapica는 스티커 좌표를 `x + width - 160` 같은 매직넘버로 박아서, 세로 레이아웃(폭 300)에서 그 값이 140이 되어 **스티커가 사진 한가운데로 들어오는 버그**가 실제로 있다. 우리는 프레임 3종 + 잠금 프레임이 있으므로 같은 사고가 확실히 재현된다.

**티켓 카드 레이아웃 (영수증 스타일, 스토리 캔버스 중앙 배치):**

```
1080 × 1920 캔버스 (배경 = 프레임 색)
  └ 티켓 카드 폭 928 (0.86W), 좌우 마진 76, 세로 중앙 정렬
      ├ 헤더  ~200 : 캐릭터 아바타 원형 + 닉네임 + 칭호 배지
      ├ BORDER 90
      ├ 4컷 2×2 : 셀 (928 - 180 - 34)/2 = 357 폭 × 268 높이 (4:3)
      │            총 블록 748 × 570  (SPACING 34)
      ├ BORDER 90
      └ 하단 턱 202 (= BORDER 90 + LEDGE 112)
           1행 45px 가운데: 「방 이름 · YYYY.MM.DD HH:mm」
           2행 27px 알파0.5 우측: 「SnapQuest · 보관 D-N」
      카드 총 높이 ≈ 1062 → 스토리 1920 안에 여유 있음
```

**하단 턱 2행에 보관 만료 D-day를 각인**하는 것은 명세 F8 예외 슬롯의 요구사항("재방문이 없으면 배너가 트리거로 성립하지 않는 순환 → 티켓 이미지에 D-day 각인")과 정확히 일치한다. Picapica가 브랜드+날짜를 넣은 그 자리다.

**사진이 4장 미만일 때** (F7 수용 기준 1번): 빈 셀을 비워두지 말고 **캐릭터 카드 / 칭호 카드**를 같은 셀 규격으로 그린다. Picapica는 로드 실패 셀을 배경색 그대로 빈칸으로 남기는데(명시적 플레이스홀더를 안 그림), 그러면 **사용자가 자기 사진이 사라진 줄 안다.**

### 3-C. Canvas 합성 — Picapica의 최대 결함을 뒤집기

#### ⑰ "합성 완료" 시점을 코드로 만들어라 (최우선)

**[Picapica가 한 것]** `drawText()` 안에서 PNG 프레임을 `new Image().onload`로 **비동기로 얹고 반환한다.** 즉 "합성이 끝났다"는 시점이 코드 어디에도 없다. 프레임 `Image`를 매 리렌더마다 새로 생성(캐시 없음). 그래서 **최초 1회는 프레임이 늦게 얹히고, 그 사이 다운로드를 누르면 프레임 없는 이미지가 저장된다.** 이걸 무마하려고 상위에서 `setTimeout(…, 100)`를 건다. 100ms 희망회로.

**[우리 어디에]** `src/lib/canvas/ticket.ts` — 신설:

```
compose(input) =
  1) await Promise.all([ ...에셋.map(loadImage), fontsReady() ])
       loadImage = img.crossOrigin='anonymous' → src 대입 → await img.decode()
  2) 단일 동기 draw 패스 (배경 → 사진 4컷 → 프레임 → 헤더 → 각인, 순서 고정)
  3) 반환 후에만 저장 버튼 enable
```

`img.onload` 카운터 대신 `img.decode()` + `Promise.all`. **같은 입력 → 항상 같은 픽셀**이 보장된다. 에셋은 모듈 스코프 `Map`에 캐시.

#### ⑱ `crossOrigin` 은 `src` 대입 **전**에, 그리고 오염을 미리 검사

**[왜]** Picapica는 모든 에셋이 same-origin `public/`이라 우연히 안전했다. **우리는 Supabase Storage에서 사진을 가져오므로 cross-origin이 확정이다.** 오염된 캔버스는 `toBlob` 시점, 즉 **사용자가 저장 버튼을 누른 뒤에야** `SecurityError`로 터진다.

**[우리 어디에]** 명세 F7 예외에 이미 "Storage CORS 헤더 + `crossOrigin='anonymous'`"가 있다. 여기에 **선제 검사** 한 줄을 추가:

```
compose 직후 → try { ctx.getImageData(0,0,1,1) } catch → 오염 확정
              → 해당 사진 셀을 플레이스홀더로 강등하고 재합성
```

저장 시점이 아니라 **합성 직후에 오염을 알아내는 것**이 핵심. 그래야 "플레이스홀더 티켓 폴백"(수용 기준 4번)이 사용자가 버튼을 누르기 전에 이미 준비된다.

#### ⑲ `document.fonts.load()` 는 "로드됨"을 보장하지 않는다

**[Picapica가 한 것]** CSS에 `font-family: Poppins`를 선언해놓고 `@font-face`도 `@import`도 없다. **아무도 눈치 못 챈 채 전원이 fallback sans-serif로 보고 있다.** 캔버스 텍스트는 `Arial` 하드코딩이라 폰트 대기 로직 자체가 필요 없는 구조였다.

**[왜]** `document.fonts.load()`는 **@font-face가 아예 정의돼 있지 않아도 빈 배열로 resolve되며 throw하지 않는다.** 명세 F7 예외의 "`document.fonts.load()` 대기 후 합성"만으로는 한글 깨짐을 막지 못한다. 이건 명세의 구멍이다.

**[우리 어디에]** `src/lib/canvas/fonts.ts` — 신설:

```
await document.fonts.load('700 45px "<우리폰트>"')   // 캔버스에 쓸 weight/size 문자열 그대로
if (!document.fonts.check('700 45px "<우리폰트>"')) → fallback 스택으로 그리고 로그
Promise.race([fontsReady, timeout(2500)])            // 상한. 폰트 때문에 티켓이 안 나오는 게 최악
```

`load()`에 넘기는 문자열은 **캔버스 `ctx.font`에 쓸 것과 완전히 동일한 weight/size 문자열**이어야 한다. 다르면 다른 face를 로드하고 check가 계속 false다.

#### ⑳ 다운로드 헬퍼는 딱 하나 — 그리고 `toDataURL`은 쓰지 마라

**[Picapica의 확정 사실]** 소스맵 주석에 남아 있다: **iOS Safari는 `toDataURL`이 만든 거대한 `data:` URL의 `download` 속성을 무시하지만 `blob:` URL은 처리한다.** `toDataURL` → `toBlob`으로 이미 한 번 마이그레이션한 흔적이다. 이건 우리가 공짜로 얻은 실전 지식이다.

그리고 Picapica는 스트립/GIF 두 다운로드 경로가 갈라져서 **한쪽만 `appendChild`·`revokeObjectURL`을 한다**(GIF 쪽은 메모리 누수 + 일부 브라우저에서 무동작). 헬퍼를 하나로 안 뽑아서 생긴 전형적 드리프트.

**[우리 어디에]** `src/lib/download.ts` — 신설, 함수 **하나**:

```
canvas.toBlob(blob => {
  URL.createObjectURL → <a download> → document.body.appendChild → click() → remove()
  → setTimeout(revokeObjectURL, 1000)
}, "image/jpeg", 0.9)
```

- `appendChild` 필수 (Firefox 등은 문서에 붙어야 click이 먹음)
- `revokeObjectURL`은 즉시가 아니라 1초 뒤 (다운로드 시작 전 revoke 방지)
- **`navigator.share({files})` 를 1순위로 시도하고 실패 시 위 blob 다운로드로 폴백.** 명세 F8 수용 기준 2번("꾹 눌러 저장 + 공유 시트")과 정합. Picapica는 `navigator.share`를 전혀 안 쓴다 — 파티 결과물은 공유가 목적이므로 우리는 여기가 1순위 버튼.
- iOS에서 blob이 "새 탭 열림"으로 끝나는 케이스에 대비해 **"길게 눌러 사진에 저장" 한 줄 안내**를 티켓 아래 상시 노출.

#### ㉑ 출력 규격을 최종 픽셀로 먼저 정하고, 입력은 그 이상으로

**[Picapica가 한 것]** 캡처는 1280×720으로 해놓고 셀에는 400×300으로 다운샘플한다 — **해상도의 90%를 버린다.** 그리고 최종 스트립이 480px 폭이라 인스타 스토리(1080×1920)에 올리면 2.25배 업스케일로 뭉갠다. QR 공유본은 원본 480보다 큰 **width 800으로 업스케일**(선명해지지 않는다).

**[우리 어디에]** F3 업로드 시점의 클라이언트 리사이즈 규격을 티켓 셀 크기에서 역산한다. 셀 폭 357 → **업로드 리사이즈 하한을 긴 변 800px**로 잡으면 2배 여유. `src/lib/image/resize.ts`(F3 리사이즈)와 `src/lib/canvas/ticket.ts`(셀 규격)가 **같은 상수 파일을 참조**하게 해서, 티켓 규격을 바꿨을 때 업로드 규격이 따라오지 않는 사고를 막는다.

표시용 캔버스와 내보내기 캔버스를 분리: **내보내기는 1080×1920 실픽셀, 화면 표시는 CSS `max-width`로 축소만.**

#### ㉒ 실패 셀은 "카운터를 막지 않는" 플레이스홀더로

**[Picapica가 한 것]** `img.onerror`에서 `imagesLoaded++`를 똑같이 올려 카운터가 막히지 않게 하고 진행한다 — **패턴 자체는 옳다**(하나 깨져도 티켓은 나온다). 다만 실패 셀을 배경색 빈칸으로 남긴다. 그리고 업로드 모드에서는 이미지 아닌 파일이 섞이면 완료 카운터가 영영 안 채워져 **진행률이 멈추고 아무것도 안 나온다**(확인된 버그).

**[우리 어디에]** `Promise.allSettled`로 에셋 로드 → 실패 건은 **캐릭터 카드로 대체**(F7의 "부족 칸은 캐릭터·칭호 카드로 채움"과 같은 코드 경로 재사용) + 상태로 올려 "N번 컷을 불러오지 못했어요" 표시. 조용한 빈칸 금지.

### 3-D. Picapica에서 훔칠 UX 결정 3

#### ㉓ 결과물을 "받으러 가기"가 아니라 "들이닥치게" — 선점 렌더링

**[무엇을]** Picapica는 마지막 컷 후 1.3초 만에 프리뷰로 **자동 이동**하고(완료 버튼 없음), 프리뷰 진입 **100ms 뒤 사용자가 요청하지도 않은 GIF를 백그라운드에서 미리 굽는다.** 사용자가 색·스티커를 만지작거리는 시간이 곧 렌더링 시간이 된다. **"생성 중" 스피너를 보여주지 않고, 사용자가 딴짓하는 창을 훔쳐서 계산한다.**

**[우리 어디에]** F9 호스트 종료 처리가 걸린 순간 **참가자 폰에서 티켓 합성을 미리 시작한다.** 4장 자동 선택(F7의 규칙 기반 AI 추천 — 인증 시각·베스트샷 득표 상위 4장)은 서버 데이터만으로 결정되므로, 사용자가 "내 티켓 만들기"를 누르기 전에 **기본 프레임 + 추천 4장 조합의 티켓이 이미 구워져 있어야 한다.** 진입 = 완성품 등장이지 로딩 화면이 아니다. 프레임/사진을 바꾸면 그때 재합성.

동시에 F7 예외의 "단체 프레임은 호스트 종료 시 서버가 자동 합성"도 같은 트리거를 쓴다 — **종료 이벤트 하나에 두 합성이 매달린다.**

#### ㉔ 제약을 사과하지 말고 규칙으로 선언하라

**[무엇을]** Picapica는 촬영 **전에 전용 화면 하나를 통째로 써서** "샷당 3초, 재촬영 없음, 4장 연속"을 공지하고, FAQ에서 "왜 재촬영이 안 되냐"를 **버그가 아니라 철학**으로 답한다("카운트다운이 긴장감과 진정성을 만든다"). 기술적 한계를 게임 룰로 프레이밍한 것.

**[우리 어디에]** F7의 AI 추천이 규칙 기반(생성형 0)이라는 걸 **"AI가 못 골라서"가 아니라 "파티가 고른 4컷"** 으로 선언한다. 4장 직접 선택도 되지만, 기본값은 파티가 정한 것. F5 네컷 타임의 "랜덤 4명 매칭"도 같은 프레이밍 — 사용자 선택권을 뺏는 게 아니라 부여한 의미가 된다.

**긴장의 축이 다르다는 점이 중요하다.** Picapica의 긴장은 *카운트다운*(시간 압박)에서 나온다. 우리에겐 카운트다운이 없다 — 사진은 이미 다 찍혀 있다. 우리 등가물은 **"어떤 4컷이 뽑힐지 모른다"**(선정의 불확실성)이고, 엔딩 연출은 **4컷이 슬롯에 한 장씩 순차로 꽂히는 리빌**이어야 한다. Picapica가 옆 레일에 썸네일을 하나씩 쌓아 진행을 보여준 그 자리다.

#### ㉕ `visibilitychange` 로 카메라·구독 재개 (모바일 필수)

**[무엇을]** Picapica는 `visibilitychange` 리스너로 포그라운드 복귀 시 카메라를 재시작한다. iOS가 백그라운드에서 스트림을 죽이는 문제 대응. 이 부분은 잘 돼 있다.

**[우리 어디에]** 명세 리스크 표에 이미 "`visibilitychange` 재구독 + 상태 재로드"가 있다. **하나의 훅으로 통합**: `src/lib/useVisibilityResume.ts` — 복귀 시 ① Supabase Realtime 재구독 ② room state 재fetch ③ (F5 촬영 중이면) 카메라 재시작. 세 곳에 각각 리스너를 다는 대신 훅 하나.

### 4-C. 우리가 의도적으로 다르게 가는 지점 (3대 차별)

1. **AI 개인화 판 vs 공용 판.** Jam은 호스트가 만든 하나의 풀에서 랜덤 서브셋을 뿌린다(GooseChase의 AI 미션 생성기도 전원 공용 리스트). 우리는 **참가자 프로필을 크로스해 인당 다른 9칸**을 만든다. 대신 그 대가로 인당 1회 LLM 호출이 필요하고, **⑩ 429가 우리 부하 피크**가 된다.

2. **AI 자동 인증 vs 근접성 치환.** Jam은 판정 문제를 통째로 회피했다(QR 스캔 = 완료). 우리는 비전 판정을 하되 **셀프체크 폴백으로 실패를 흡수**한다 — 이 조합이 성립하려면 **② 미션이 애초에 판정 가능하게 생성**되어야 한다. 그렇지 않으면 전부 폴백으로 새고 차별점이 증발한다.

3. **파티 중 모인 사진으로 조립하는 엔딩 vs 즉석 촬영.** Picapica의 긴장은 카운트다운, 우리는 **선정의 불확실성**(㉔). Picapica의 업로드 모드가 우리 유스케이스인데 거기가 가장 약하므로(P1), **뒤집으면 그대로 차별점**이다.

### SnapQuest 측 미검증

- **Gemini 비전 판정의 실제 정확도** — 저조도 파티 조명에서 "2인 이상 프레임" 판정이 몇 %나 성공하는지 데이터 없음. **셀프체크 폴백 비율이 예상보다 높으면 F3의 차별점이 흔들린다.** 시드 이미지 10장으로 사전 측정 권장.
- **Gemini 429 임계값** — 15명 동시 입장 시 30콜이 실제로 한도를 넘는지 미측정. ⑩의 대비는 예방적.
- **한글 웹폰트의 캔버스 로드 시간** — 한글 폰트는 서브셋 없이 수 MB다. `timeout(2500)`이 적절한 상한인지 미검증. 서브셋(닉네임·칭호에 쓰이는 글자 범위) 없이는 2.5초를 넘길 가능성이 있고, 그러면 **전원이 fallback으로 티켓을 받는다.** 실측 필요.
- **`rooms` JSON 1개 vs 실제 스키마 불일치** — 명세는 "게임 상태는 rooms 테이블 JSON 1개"라고 쓰여 있으나, `supabase/migrations/0001_init.sql`은 이미 `rooms / participants / photos / votes` 4테이블로 구현되어 있고 board·title·ticket은 `participants` 컬럼이다. **이게 옳다** — jam-tech가 지적한 "200명이 동시에 같은 JSON 문서를 갱신하는 write 경합"을 이미 회피했다. **명세 문구를 코드에 맞춰 고칠 것.**
- **`?role=tv/host/player`의 실제 라우팅 구현** — 명세는 쿼리 파라미터, 위 체크리스트는 `/tv`·`/host`·`/play` 경로로 적었다. 어느 쪽인지 미확정. **쿼리보다 경로가 낫다** — 소셜 프리뷰·not-found·프리렌더가 전부 경로 기준이고, `?role=` 은 Jam이 `?goto=`·`?fromSpreadList=` 를 쓴 것과 달리 **일시적 플래그가 아니라 영구적 화면 정체성**이라서. 랜딩에서 리다이렉트만 걸면 명세의 세 링크는 그대로 유지된다.
